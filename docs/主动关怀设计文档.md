# 主动关怀机制 · 设计文档

> 本文档说明"AI 通过手环/手表数据主动关心用户"这套机制的完整思路，
> 数据源无关（小米手环 / Apple Watch / 华为 / Garmin 都能套），
> 只写通用的**判定、节流、生成、发送**逻辑。

---

## 一、整体架构

```
 ┌─────────────┐   定时轮询    ┌──────────────┐   写入    ┌──────────────┐

                                     │                          │
                                     ▼                          ▼
                             ┌───────────────────────────────────────┐
                             │            异常判定 Detector           │

                             │  2. 个体基线 z-score (今天 vs 最近 N 天)│

                             └──────────────┬────────────────────────┘
                                            │

                                            │
```

## 二、核心概念

### 1. 数据快照 (Snapshot)

每次轮询把手环/手表上的所有关键指标拉下来，压成一份**当日快照**：

```json
{
  "date": "2026-09-11",
  "timestamp": 1757580000,
  "max_hr": 128, "min_hr": 52, "avg_hr": 74, "latest_hr": 71,
  "sleep_score": 82,
  "spo2": 96,
  "steps": 3120,
  "period": { "phase": "luteal", "days_to_next": 5 }
}
```

**关键点**：只存**当日已发生**的聚合值，不存原始波形数据。原始点太多、意义不大。

### 2. 滚动基线 (Baseline)

保留最近 **N 天**（默认 7 天）的每日快照，用来算个体基线均值/标准差。

```json
{
  "history": [ {日1}, {日2}, ..., {日7} ],
  "cooldowns": { "heart_rate_high": 1700000000.0, ... },
  "last_care_ts": 1700000000.0
}
```

**为什么要个体基线**：绝对阈值（比如"心率>100"）对每个人都不合适，
运动员静息心率 45，普通人 70，用同一把尺子会误报炸开。
用**这个人最近 7 天的均值±2σ**，判定就是"她今天比她自己平时高"。

### 3. 异常判定 Detector

三类规则组合使用：

| 类型 | 例子 | 何时触发 |
|------|------|----------|
| **绝对阈值** | 血氧 < 93% | 数值本身危险，不需要对比 |
| **z-score 基线** | 心率 z ≥ 2.0（比平时高 2 个标准差） | 需要至少 3 天历史 |
| **时间窗规则** | 23:30 后心率仍高于日均 | 结合当前时刻做判定 |

每条 alert 输出一个 dict：

```python
{"key": "heart_rate_high", "type": "心率偏高", "hint": "宝宝今天心跳比平时快了一些"}
```

`hint` 是喂给 LLM 的**自然语言描述**，不要塞数字（LLM 一见数字就想复读）。

## 三、过滤层（决定"不打扰"体验的关键）

主动关怀最容易翻车的地方不是判定不准，是**打扰过度**。这五层过滤缺一不可：

### 1. 冷却时间 (Cooldown)

每类事件独立冷却，命中一次后 N 小时内同类不再推：

```python
COOLDOWN_HOURS = {
    "heart_rate_high": 4,
    "heart_rate_low": 4,
    "sleep": 8,             # 睡眠一天最多提一次
    "spo2": 4,
    "late_night": 6,
    "lazy_step": 20,        # 步数偷懒 = 每天最多一次
}
```

### 2. 静默时段 (Quiet Hours)

默认 23:00~07:00 不发。防止半夜误触把人吵醒。

```python
def in_quiet_hours(now, start="23:00", end="07:00") -> bool:
    ...
```

**注意跨日**：起始 23:00 结束 07:00 是跨零点的，判定要写对。

### 3. 聊天窗口 (Chat Gap)

**这条很关键**——如果用户 10 分钟内刚跟 AI 说过话，就别推。
否则用户体验上会变成"我明明在跟你聊天，你还突然冒一句关心我，很割裂"。

实现方式：hook 用户消息事件，记录 `_last_user_msg_ts[session_id]`，
判定时对比 `time.time() - ts < gap * 60`。

### 4. 数据陈旧保护 (Stale Guard)

手环数据不是实时的，用户不打开 App 云端数据就不刷新。
如果 snapshot 时间戳距今 > 2 小时，直接跳过——不能拿昨晚的数据触发今早的关心。

### 5. 会话级插件开关

如果用户在某个会话手动关了插件，主动关怀也要跟着关。
框架不会自动拦截 LLM Hook 和后台任务，**必须在推送前手动判断一次**。

## 四、LLM 文案生成（防 OOC 的关键）

### ❌ 反面教材

```python
prompt = f"用户健康数据异常: {alert}。请生成一句关心话。"
resp = await llm.text_chat(prompt)
```

裸调 LLM，没人设、没上下文，生成出来的东西必然是**AI 助手腔**——
"亲，注意休息哦~"、"记得多喝水昂~"，或者堆一堆"肚肚""坠坠的疼"这种幼稚化词。

### ✅ 正确做法

```python
async def compose_message(alert, session_id):
    provider = context.get_using_provider()

    # 1) 用户内心独白模板 (可让用户在配置里自定义)
    prompt = template.format(hint=alert["hint"], time=now_str)

    # 2) System Prompt: 优先从当前会话对应 persona 里读, 而不是空
    system_prompt = await resolve_system_prompt(session_id)

    # 3) Contexts: 带上最近 4 轮对话, 让口吻贴合当下语境
    contexts = await resolve_recent_contexts(session_id, turns=4)

    resp = await provider.text_chat(
        prompt=prompt,
        contexts=contexts,
        system_prompt=system_prompt,
    )
    return resp.completion_text or fallback_text(alert)
```

**三个必带**：
- **人设 System Prompt**：直接复用用户主对话里的 persona，不要另写一套
- **最近对话上下文**：4 轮左右，让 LLM 知道"刚才在聊啥"，避免话题割裂
- **兜底文案**：LLM 挂了/超时，用每类事件预写的固定短句兜住，不能什么都不发

### Prompt 模板设计

模板要**留占位符 + 让用户自己改**，不要写死在代码里：

```
[内心独白] 我刚扫了眼她今天的身体数据, 注意到: {hint}。
现在时间 {time}, 我想以我自己的口吻自然地对她说一句关心。

严格要求:
- 保持我一贯的说话方式, 不要堆语气词、不要连续叠字撒娇
- 不要用"肚肚""趴着眯""哼哼""坠坠的疼"这类幼稚化词汇
- 不要报警式复述数据, 不要一次问一堆问题
- 一到两句短句, 平静、克制、不催促, 像随口关心一句
- 直接输出这句话本身, 不要任何前缀/旁白/解释
```

关键是那句**"直接输出这句话本身，不要任何前缀/旁白/解释"**——
不然 LLM 经常会返回 `"好的，我来说：xxx"` 这种。

## 五、Apple Watch 迁移建议（针对你朋友）

小米手环这边是靠**小米云 API**（web.mifit.iot.mi.com）扒数据，
Apple Watch 那边应该走 **HealthKit**：

### 数据获取
- iOS 原生 App：用 `HKHealthStore` 直接读 `HKQuantityType.heartRate` / `sleepAnalysis` / `oxygenSaturation`
- 如果 AI 后端在服务器（不在手机上）：iOS App 端定时把关键指标推到自己的后端，
  或者用 [Apple Health Auto Export](https://www.healthyapps.dev/) 这种第三方 App 自动导出

### 数据颗粒度差异
- Apple Watch 是**分钟级采样**，比小米手环细得多，可以做更精准的实时判定
- 但也意味着**数据量更大**，快照层要注意只存聚合值，别把原始点存进基线库
- 血氧和睡眠 Apple 家更权威，可以适当放宽阈值（spo2 < 94 触发都合理）

### 独有指标
Apple Watch 有几个小米没有的指标，可以加进来：
- **HRV (心率变异性)**：压力检测的黄金指标，z-score 判定压力大
- **静息心率 (Resting HR)**：比 avg_hr 更稳定的个体基线
- **VO2max**：长期趋势能看出运动能力变化
- **手洗提醒 / 摔倒检测**：这些 Apple 已经做了，AI 别重复

### 架构差异
- iOS 沙盒限制严，后台轮询会被系统杀掉，最好走**推送模式**：
  手表/手机 App 检测到异常 → HTTP 通知 AI 后端 → AI 生成关怀话发回
- 不要在手机端跑 LLM，太耗电，全部走后端

## 六、可配置项清单（给用户自己调）

好的插件要允许用户细调，不然默认值再合理也会踩到某些人的雷。至少要暴露：

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `monitor_enabled` | false | 主动关怀总开关 |
| `check_interval` | 900s | 轮询间隔 |
| `baseline_days` | 7 | 基线保留天数 |
| `quiet_hours_start/end` | 23:00 / 07:00 | 静默时段 |
| `recent_chat_gap_minutes` | 10 | 聊天窗口 |
| `stale_threshold_hours` | 2 | 数据陈旧阈值 |
| `heart_rate_zscore` | 2.0 | 心率异常敏感度 |
| `sleep_zscore` | 1.5 | 睡眠异常敏感度 |
| `spo2_abs_threshold` | 93 | 血氧绝对阈值 |
| `care_prompt_template` | (见上) | LLM Prompt 模板 |
| `care_system_prompt` | 空 | 人设覆盖，留空自动继承 |
| `care_use_recent_context` | true | 是否带最近对话 |
| `care_context_turns` | 4 | 带几轮 |
| `fallback_*` | 每类一句 | LLM 挂了的兜底文案 |

## 七、常见坑

1. **别在 LLM Prompt 里塞具体数值**。塞了 LLM 就会复读"你心率 128"，
   完全破坏"随口关心"的自然感。用自然语言 hint 描述就够了。

2. **别用绝对时刻触发**（比如"每天 10 点问一次早"）。
   要用数据触发（"睡眠评分低" / "步数少"），不然就退化成定时闹钟了。

3. **冷却时间要按类型分开**，不要一个全局冷却。
   否则"心率异常"和"睡眠差"会互相抢冷却时间。

4. **首次运行要有基线建立期**。
   前 N 天数据不够，z-score 判定会失真，只跑绝对阈值检测就好。

5. **上下文要真的带进去**，不是 System Prompt 里写一句"你叫小明"就完事。
   Contexts 参数必须传最近的对话 message 列表，LLM 才有"我们刚在聊什么"的感知。

6. **兜底文案不能没有**。LLM 有可能超时、限流、返回空，
   每类事件写一句人话的固定文案兜底，用户体验才稳。

## 八、参考实现

小米手环版本的完整实现在这个仓库，核心文件是 `core/monitor.py`：

- `HealthMonitor._tick()` 主循环
- `HealthMonitor._detect()` 判定规则
- `HealthMonitor._compose_message()` LLM 文案生成
- `HealthMonitor._resolve_care_system_prompt()` 人设加载
- `HealthMonitor._resolve_care_contexts()` 对话上下文加载

Apple Watch 版本把 `mi_client` 换成 HealthKit / 你朋友自己的数据源 SDK，
其它逻辑基本可以照搬。
